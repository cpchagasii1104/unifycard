estas regras. Se um módulo passar nos gates locais mas violar uma destas
regras, o módulo está errado — não a regra.

Alterações aqui exigem RFC formal em docs/02_decisions/.

T2 — CONCEPT_ID EM BANK_TRANSACTIONS (EM EXECUÇÃO)
--------------------------------------------------------------------------------
  Campo:              bank_transactions.concept_id UUID
  FK:                 → concepts(concept_id) ON DELETE RESTRICT
  RFC base:           docs/02_decisions/RFC_C2_rollout.md (Opção B — NULL-first)
  RFCs auxiliares:    docs/02_decisions/RFC_C2_bank_transactions_concept_link.md
                      docs/02_decisions/RFC_C2_seed_concepts_financeiros.md
                      (24 concepts em 7 domínios financeiros)
  Regra:              todo INSERT em bank_transactions deve declarar concept_id;
                      sem concept_id válido, a operação financeira carece de
                      significado (LEI §4.10.6).
  Proibido:           - inferir concept_id por contexto implícito
                      - default automático / fallback de concept_id
                      - omitir concept_id em qualquer call site de produção
                      - usar placeholder (ex: "SCRIPT E2E") como concept
  Resolução do concept_id em runtime — categorias permitidas:
                      - LITERAL (hardcoded no call site, ex: "literal 'escrow-hold'")
                      - BRANCH_CONDITIONAL (if/switch dentro do método —
                        a condição exata deve ser citada, ex:
                        "if (referenceType === 'event_ticket')")
                      - PARAM (vem de parâmetro da função — citar nome,
                        ex: "input.referenceType")
                      - METADATA (vem de campo de contexto/evento — citar
                        caminho, ex: "event.metadata.kind")
                      - PROPAGATED (wrapper que apenas repassa do caller —
                        ex: "input.concept_id (propagated from caller)")

COMO USAR ESTA SEÇÃO
--------------------------------------------------------------------------------
  Ao auditar/criar módulo:
    1. Ler esta seção COMPLETA antes de tocar em código
    2. Verificar conformidade contra T1-T8
    3. Documentar violação encontrada com identificador (ex: C26)
    4. Só dar PASS no módulo após T1-T8 satisfeitos
  Ao revisar mapeamento topológico (3-B style):
    1. Cada call site deve declarar como o concept_id é resolvido
       (LITERAL / BRANCH_CONDITIONAL / PARAM / METADATA / PROPAGATED)
    2. Nenhum call site de produção pode ter origem indefinida
    3. Branches condicionais devem citar a condição literal (não basta
       dizer "branch condicional" — precisa ser "if (X === 'Y')")
    4. Scripts não-produtivos (dev/CI) devem ser marcados FORA DO ESCOPO
  Ao adicionar nova decisão transversal:
    1. RFC em docs/02_decisions/
    2. Após DECIDIDO, adicionar entrada T9 (próximo) com referência ao RFC
    3. Atualizar gates CI se aplicável
